The admission gate in server.py now uses only ledger-based projections to decide requests. The formula is reserved_mb plus ollama_mb plus requested_mb must be less than or equal to gpu_total minus SAFETY_MARGIN_MB. This change fixes a bug that double-counted idle VRAM as both live usage and the configured margin.

Live GPU usage is still read on every admission attempt, but it now serves only anomaly detection. A warning log flags unexpected spikes versus the sum of SAFETY_MARGIN_MB and reserved_total. The docstring at server.py line 306 was updated to document this new formula and rationale. No changes are needed in .env, .env.example, or plan.md.

Two regression tests were added in tests/test_server.py to reproduce the original incident numbers. One test uses gpu_total of 12282 and a margin of 4864. A request for 5120 MB was previously rejected even though about 9060 MB was physically free. The fix now grants this request, so one test confirms that behavior. Another test confirms an 11000 MB request still times out.

The existing test_queue_timeout_when_no_room was adjusted because it relied on live usage alone to trigger the old gate refusal. Its request size changed from 1000 to 7000 MB. A Resolved addendum was appended to Assist/ISSUE_double_counted_margin.md to document this fix and its scope deviation. The original issue doc noted not to touch the max() term, but that term is now repurposed for anomaly detection rather than gate input. Live broker verification against a real running instance confirms the change.
